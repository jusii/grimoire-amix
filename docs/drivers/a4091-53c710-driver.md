# Case Study: A4091 / 53C710 SCSI driver

This is the deep end of the [drivers pillar](driver-model.md): writing a **brand-new SCSI host
adapter driver** for Amix, for a board the OS was never meant to support, and getting Amix to
**boot with root, swap and filesystem entirely on it**. It pulls together the
[device-driver model](driver-model.md), [Zorro AUTOCONFIG](zorro-autoconfig.md), the
[kernel build](kernel-build.md) and the [boot process](../how-it-works/boot-process.md) — all the
other driver pages applied at once to a real board.

The work is **first-party and reproduced locally** in Amiberry on the real Amix 2.1c distribution.
Claims tagged ✅ below were reproduced on the running system; 🟡 claims are emulation-only and need
real-hardware confirmation; 🔴 marks a belief we held and disproved. The source is the
[A4091-on-Amix project](#sources) — `src/a4091-wr.c`, the `src/kernel-patches/`, `driver.conf`,
and its `CHANGELOG.md` and `docs/`.

## What the A4091 is

The **A4091** is Commodore's **Zorro III** SCSI-2 host adapter, built on the **NCR/Symbios 53C710**
SCSI I/O processor ✅. It is the high-end successor to the Zorro II A2091 (WD33C93), intended for the
A3000T/A4000T class.

Its AUTOCONFIG identity and memory window ✅ (`src/a4091-wr.c`, `docs/a4091-53c710-reference.md` §0):

| Property | Value | Source |
|---|---|---|
| AutoConfig manufacturer | `0x0202` (Commodore) | `a4091-wr.c` `A4091_PROD` |
| AutoConfig product | `0x54` | `a4091-wr.c` `A4091_PROD` |
| Combined product id | **`0x02020054`** | `a4091-wr.c` `#define A4091_PROD 0x02020054` |
| `er_Type` | `0x90` (Zorro III) | reference §0 |
| Physical board base | **`0x40000000`** | `a4091-wr.c` `a4091map()` fallback |
| Board window | **`0x01000000`** (16 MB), sparse | reference §1 |
| 53C710 register block | board + **`0x00800000`** → `0x40800000` | `a4091-wr.c` `SIOP_OFF` |

Amix (Commodore's SVR4.0 port to 68030 Amigas, the "2.1c" distribution ✅) **shipped with no 53C710
driver** and is widely described as **Zorro II only** ✅ — see [Zorro AUTOCONFIG for drivers](zorro-autoconfig.md)
and [Supported hardware](../how-it-works/hardware.md). The stock kernel only knows the A2090/A2091
(WD33C93) and the A3000 on-board SCSI. This project wrote a native 53C710 block driver and made the
A4091 a first-class, auto-detected SCSI controller alongside them.

## The Zorro III obstacle and the `sptalloc()` solution

The board is in **Zorro III** space, and that is exactly where the stock drivers' trick breaks down.

🔴 **"Zorro III is unaddressable" — was thought absolute, is actually an unmapped address range with
a work-around.** Amix identity-maps only the **low 1 GB** of physical address space,
`0x00000000`–`0x3FFFFFFF` ✅. That leaves **`0x40000000`–`0x7FFFFFFF` unmapped — and the A4091 sits
in it** ✅. Zorro II boards are ≤ 24-bit (e.g. the A3000 SCSI at `0xDD0000`), so they fall inside the
identity map; that is why the stock WD33C93 drivers can simply dereference the address `autocon()`
returns. Extending the identity map upward to cover the gap is **unsafe** — `amiga/ml/syms.s` places
the page-mapped u-area at `0x40000000` ✅.

> **Correction (2026-08-14).** This section previously attributed that identity map to the 68030's
> Transparent-Translation registers (`tt0 = 0x003F0143` / `tt1 = 0x807F0143`, from
> `amiga/ml/ttrap.s`). AMIX does **not** use the TT registers — they read E = 0 on a running kernel,
> the boot path zeroes them, and the identity map is a **section-0 early-termination page descriptor
> in the MMU root table** ✅. Nothing below changes; see
> [how the low 1 GB is really mapped](zorro-autoconfig.md#the-identity-map).

**The fix** is the kernel primitive **`sptalloc(npages, prot, pfn, flag)`**, which page-table-maps
physical pages into kernel virtual address space ✅. The driver maps the board's AutoConfig page and
the 53C710 register block (`src/a4091-wr.c`, `a4091map()`):

```c
#define	SIOP_OFF	0x00800000	/* 53C710 register block within the board window */
...
acfg = (volatile uchar *)sptalloc( 1, PG_V, phystopfn( (paddr_t)base), 0);          /* board base    */
siop = (volatile uchar *)sptalloc( 1, PG_V, phystopfn( (paddr_t)base + SIOP_OFF), 0); /* 53C710 regs */
```

Post-boot these return working kernel VAs (observed `siop = 0x401CA000`) and the 53C710 is fully
addressable ✅. **DMA is unaffected:** the 53C710 bus-masters to Amix RAM at phys `0x07800000+`,
which is inside the identity-mapped low 1 GB, so DMA targets are reachable no matter where the
board's *registers* land in kernel VA ✅. (See [Zorro AUTOCONFIG](zorro-autoconfig.md) for `autocon()` and the Zorro III
detection that complements this mapping.)

`sptalloc()` is the **68030** build's mapping. The 68040/68060 arm of the same driver
(`-DA4091_KVA`) cannot use it, because there `sptalloc()` gives a cacheable page: it maps both
register pages non-cacheable with `dev_kvmap()` and sends every transfer through a DMA-coherence
service (the project's `docs/D42-CALL-SHAPE.md`) ✅. "DMA is unaffected" is the 68030 line's rule
only; the 030 build does no cache maintenance, which is justified in emulation (data cache off)
only 🟡.

## The 53C710 driver model — how it plugs into the Amix SCSI stack

✅ The Amix SCSI stack (`amiga/alien/`) layers like this:

```
block disk driver dd.c / gsioctl passthrough  ->  sd.c selector  ->  per-card queue function  ->  chip
```

The command unit handed down the stack is `struct sdcom` (`sd.h`): `cdb[12]`, the data `addr`/`nbyte`,
`unit`/`card`, the `reading` flag, `status`/`okay`, and an `intr()` completion callback ✅. See
[the device-driver model](driver-model.md) for the general switch-table mechanism this sits on top of.

### The card registry in `sd.c`

`sd.c` carries a registry table `scsicard[]` mapping AutoConfig product ids to queue functions. The
project ships no `sd.c`: its `driver.conf` lists one row per board the driver binds, and
amix-kerntools' `amix-build` generates the `sd.c` additions from it (`gen_sd_patch`) ✅:

```c
static struct {
	uint	pn;				/* product number */
	bool	(*f)( );			/* queuing function */
	char	*hardwarename;
} scsicard[] = {
	0x0202F003, &a3091queue, "A3000 Internal SCSI",
	0x02020001, &a2090queue, "A2090 SCSI",
	0x02020003, &a2091queue, "A2091 SCSI",
	0x02020054, &a4091queue, "A4091 SCSI",   /* <- generated from driver.conf */
	0xc0de0001, &a4091queue, "A4092 SCSI",
	0xc0de0002, &a4091queue, "A4770 SCSI",
};
```

At the first root open, `sd.c init()` calls `autocon(productid, …)` for each row and `insert()`s the
cards it finds, **sorted ascending by board base address** ✅:

```c
static void
init( )
{
	if (not queue->f)
		for (i=0; i<nel( scsicard); ++i) {
			int c = 0;
			while (autocon( scsicard[i].pn, c, &a, &o))
				insert( scsicard[i].f, c++, a, scsicard[i].hardwarename);
		}
}
```

So on a machine with both controllers, the A3000 SCSI (`0xDD0000`) becomes `queue[0]` (**card 0**)
and the A4091 (`0x40000000`) becomes `queue[1]` (**card 1**) — the lower base sorts first ✅. **This
ordering is the entire story behind booting root from the A4091** — see
[the boot process: root on an A4091](../how-it-works/boot-process.md) and the phantom-A3000 fix in
[Zorro AUTOCONFIG](zorro-autoconfig.md).

> **Why the stock ordering cannot be trusted at all.** Stock `autocon()` decides whether the A3000
> internal SCSI exists from **where the kernel was loaded** (`end > 0x07000000` in `support.c`, `end`
> being the kernel's own end address), never from the hardware ✅ — so it fabricates a card 0 where no
> controller exists *and*, on a machine where the kernel loads lower, silently drops the real one (root disk included) while every
> remaining card renumbers ✅. Both directions produce a machine that cannot find its disk and says
> nothing. **Probe, don't guess** — see [quirks §41](../how-it-works/quirks.md#41-scsi-by-ram-size)
> and the chipset-gated WD33C93 probe that replaces the special case.

`amix-build` also generates the matching `amiga/alien` Makefile edit, which adds `a4091.o` to the
`OBJ` list (`gen_makefile_patch`); the project does not ship it.

### The driver itself: `a4091-wr.c`

The production driver is `src/a4091-wr.c` (the READ+WRITE driver) ✅. Its key pieces:

- **`a4091map()`** — `sptalloc`-maps the board base and the register block (above; `dev_kvmap` on
  the 040/060 arm), and **caches the mapping** per card so it only happens once. The 68030 build
  falls back to the known base `0x40000000` if no base was recorded for the card; the 040/060 arm
  has no fallback and treats that as "no board" ✅.
- **`a4091init()`** — a 53C710 soft reset followed by minimal **polled-mode** register init. Reset is
  via **ISTAT bit 6** (not DCNTL — that is the older 53C700) and is **not self-clearing**, so it is
  set then explicitly cleared. The init writes `SCNTL0=0xCC`, `SCNTL1=0x20`, `DCNTL=0x00`,
  **`DMODE=0xE0`** (burst-8 | FC2, the A4091 value), the one-hot host id `SCID = 1 << 7 = 0x80`, and
  the A4091 bus-arbitration errata bit `CTEST8 |= 0x01` (SM). No SCSI/DMA interrupts are enabled ✅.
  All register **writes go to `reg + 0x40`** (the A4091 write-shadow `WRSHADOW`), reads at `reg + 0`;
  accesses are **8- or 32-bit only, never 16-bit** ✅.
- **`a4091queue(c, cp)`** — drives **any** CDB from the caller's `sdcom` through a **table-indirect
  53C710 SCRIPTS program** (`inq_script[]`, a static `ulong[]` that lives in kernel `.data`, so its
  bus address equals `&inq_script[0]` under the low-1 GB identity mapping). CDB length is derived from the
  SCSI **group code** (top 3 bits of the opcode → 6 / 10 / 12 bytes). The **DSA** (`struct siop_ds`)
  binds IDENTIFY / CDB / status / message / data buffers; the DATA phase **dispatches on the live bus
  phase**, so *one* SCRIPTS program performs both READ(10) and WRITE(10). Data DMAs **straight into
  `cp->addr`** — the caller's buffer, already a physical address via `dd.c`'s `vtop()` ✅.

The SCRIPTS program's data-phase dispatch (from `inq_script[]` in `src/a4091-wr.c`) is what makes one
program serve reads and writes:

```c
0x808b0000, 0x00000018,		/* JUMP dataout, WHEN DATA_OUT  (write)         */
0x818b0000, 0x00000020,		/* JUMP datain,  WHEN DATA_IN   (read)          */
0x838b0000, 0x00000020,		/* JUMP status,  WHEN STATUS    (no data)       */
```

The DSA table binds the caller's buffer for the data move ✅:

```c
ds.data1len = cp->nbyte;  ds.data1buf = (uchar *)cp->addr;	/* DMA -> caller buf */
```

#### Completion: a bounded ISTAT poll {#completion-the-one-honest-in-the-driver}

After launching SCRIPTS (a write to `R_DSP`), the driver **spins on ISTAT** until `SIP` or `DIP` is
set or a bound of 8 000 000 reads runs out ✅:

```c
WR32( R_DSP, (ulong)inq_script);
/* bounded-poll completion -- spin on ISTAT until SIP|DIP or the bound */
while (poll < limit) {
	istat = RD8(R_ISTAT);
	if (istat & (ISTAT_SIP | ISTAT_DIP)) break;
	poll = poll + 1;
}
...
if (!(istat & (ISTAT_SIP | ISTAT_DIP)))         rc = -2;	/* bound ran out */
else if (sstat0 & SSTAT0_STO)                   rc = -1;	/* selection timeout */
else if ((dstat & DSTAT_SIR) && dsps == 0xff00) rc = 0;		/* SCRIPTS "done" INT */
```

The bound exists because the same path runs the boot-time SCSI bus scan, which must not hang on an
empty id ✅. After a short-read resume the driver re-polls the same way, and it keeps
`a4091_maxpoll` (the high-water poll count) and the `a4091_slow_poll` console threshold so the cost
on a physical disk can be read back ✅. This completion ran on metal in the 68040/68060 build — the
A4092 results [below](#zorro-iii-dma-into-a-z3660s-cpu-ram-the-first-metal-data-point-2026-10-02)
came through it 🟡 (one machine). Interrupt-driven completion is not implemented: the driver enables
no SCSI/DMA interrupts. The early prototypes (`a4091-nopoll.c`, `a4091-blk.c`) used a **single
ISTAT read**, which works only because the **emulated** target answers synchronously ✅.

For the full 53C710 register map, SCRIPTS encoding, one-hot SELECT-ID encoding, the soft-reset
sequence, the write-shadow at `reg+0x40`, and the emulator's full-window SIGSEGV hazard, see the
project's `docs/a4091-53c710-reference.md` (the verified chip reference behind this driver).

## The A4091 disk's `/dev` numbering

✅ With both an A3000 and an A4091 present, the A4091 (card 1) target 0 slice 0 is reached at:

```
/dev/dsk/c8d0s0    block, major 18, minor 8
/dev/rdsk/c8d0s0   char,  major 40, minor 8
```

The `cN` in the name is **computed**, not stored — see the SCSI minor-number scheme on the
[device list](../reference/device-list.md#minor-number-encoding-for-the-scsi-disk-major-18). From
`amiga/alien/sd.h`:

```
sdunit(dev) = (dev>>0) & 7      /* SCSI target id 0-7        */
sdcard(dev) = (dev>>3) & 1      /* card index (queue[] slot) -- only 0 or 1; SDCARDS = 2 */
sdpart(dev) = (dev>>4) & 7      /* slice/partition           */
```

So `cN = sdcard*8 + sdunit`: `c8d0s0` = card 1, target 0, slice 0 = `makedevice(18, 8)`; the stock
A3000-root device `c6d0s1` = card 0, target 6, slice 1 = `makedevice(18, 22)` ✅. A `dev_t` is
`(major << 18) | minor` ✅.

The READ/WRITE path was validated end to end ✅:

- **Raw SCSI passthrough** via the `gsioctl` userspace path (`src/gsio.c`, `/dev/scsi` major 11) —
  INQUIRY, READ(10), WRITE(10) all returning correct data.
- **`mkfs ufs` + `mount`** on the A4091 disk, with files written and **surviving a reboot** (genuine
  persistence to the disk behind the A4091, not a RAM artefact).

## Build & install

The driver is a standard kernel-relink job ([kernel build & install](kernel-build.md)), with the
A4091-specific steps:

1. **Drop the driver** `src/a4091-wr.c` into the kernel tree as `/usr/sys/amiga/alien/a4091.c`.
2. **Register it in the Makefile** — add `a4091.o` to the `amiga/alien` `OBJ` list (generated
   from `driver.conf` by amix-kerntools' `amix-build`).
3. **Add the SCSI-stack rows** — the `scsicard[]` rows in `sd.c`, also generated from `driver.conf`
   by `amix-build`.
4. **Apply the auto-detect patch** — the chipset-gated `autocon()` in `support.c`
   (`src/kernel-patches/support.c.patch`); this is what lets one kernel boot both an A3000 and an
   A4000+A4091. The why is on [Zorro AUTOCONFIG](zorro-autoconfig.md) and
   [the boot process](../how-it-works/boot-process.md).
5. **Build with the clean-gate.** The Amix `ld` intermittently corrupts the linked kernel
   (the "D245 boot-breaker"); relink until the checksum recurs rather than trusting a single `make`.
   Use `tools/build-clean-kernel.sh` and verify with `tools/relsim.py` / `checkunix.c` — full detail
   on [kernel build & install](kernel-build.md). **Never `make install` an unverified kernel onto
   your working disk** — it rewrites the boot partition and bricks it if the kernel is corrupt.
6. **Install carefully** onto a throwaway / clone disk — see
   [adding drivers to a custom boot disk](../boot-disks/adding-drivers-to-boot-disk.md) and the
   "boot root on the A4091" install recipe on [the boot process](../how-it-works/boot-process.md).

> **Tip — cross-develop on a modern host.** As of 2026-06 you can build the driver object on Linux with the [`gcc-cross-amix`](https://github.com/isoriano1968/gcc-cross-amix) cross-toolchain (`m68k-cbm-sysv4-gcc`) instead of editing on the box — it cross-compiles a real Amix driver `.c` to a relocatable m68k ELF; you then do only the final relink on Amix. See [Toolchain → cross-compiling](toolchain.md#cross-compiling-on-linux-the-gcc-cross-amix-toolchain). ✅

The SCRIPTS source (`reference/scripts/inq-wr.ss`) is assembled with the **NetBSD `ncr53cxxx`**
assembler from the open-source [a4091.device project](https://github.com/A4091/a4091-software), which
also provides the A4091 autoboot ROM used by the emulator
([Amix on Amiberry](../getting-started/emulation-amiberry.md)).

### Zorro III DMA into a Z3660's CPU RAM — the first metal data point (2026-10-02)

Can a Zorro III **bus master** reach the RAM on a Z3660 accelerator? For one setup the answer is
**yes** ✅: on an **A4000D** (Buster -11) with a **Z3660 in real-68LC060 mode**, an autoconfigured
**A4092** (53C710, card CPLD 1.4.21, at `0x40000000`) DMAs into the Z3660's **CPU-local RAM at
`0x08000000`**, the memory the Amix kernel runs from. The kernel was a 68060 Amix kernel with this
driver and a DMA cache-coherence service; with copyback caching on, LBA 0 reads back as a valid RDB,
4 MB and 32 MB raw reads give the same checksum on every read and across power-cycled boots, and the
coherence service's invariants held over about 72 MB of device-to-memory transfers ✅. The data is
also **right**, not merely repeatable ✅: a host copy of the disk image (104 857 600 bytes, pulled without
the Amiga's network, every 8 MiB piece CRC-checked against the device) has the same `sum -r` at
4 MiB (`49574`, matching the Amix reads on both boots) and at 32 MiB (`09482`, matching both reads on
the first boot) and the same block 0. So the read direction — device to Z3660 RAM — is coherent ✅.
The **write** direction (memory to device) and root on the A4092 followed on the same A4000D + Z3660
with the same driver arm 🟡 (one machine): on 2026-10-03 the A4092 carried the root filesystem
through two full boots, and on 2026-10-11 the hardware acceptance of the 1.0 install media installed
the 30-package set onto a 512 MB disk behind the A4092 (`c9d0`) in 1 h 45 min, with a clean final
`fsck` and a booting system.

**Why the read direction can be coherent in hardware** 🟡. The Z3660's CPLD drives the 68060's
`SNOOP` input low on every cycle of its own DMA engine and whenever the ARM holds the bus
(`z3660.vhd` line 459 in the flashed `DMA_WIP` design; the firmware's CHANGES for v1.03 beta 2 note
the SNOOP change) ✅ (read from the source). Per the MC68060 bus-snooping rules as commonly
described, a snooped **write** by another master invalidates a matching data-cache line, while a
snooped **read** is *not* supplied from a dirty cache line (the 68040's snoop-sourcing was dropped
on the 68060) — the manual is not in this project's sources, so this half is 🟡. If that holds,
DMA *into* Z3660 RAM is coherent without software help, and DMA *out of* it is not: a driver must
push dirty cache lines to memory before a device reads them. Earlier cautions that Zorro DMA cannot
reach a Z3660's memory concerned RAM autoconfigured *into* Zorro space; they do not describe this
CPU-local aperture 🟡. Registering the A4092 at all needed the stock-kernel fix in
[quirks §65](../how-it-works/quirks.md#65-autocon-signed-manufacturer).
